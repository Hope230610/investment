## Context

当前 `structure/` 已经冻结了正式认证、安全治理和统一错误响应基线，但真实代码仍停留在偏 MVP 的实现状态：

- `investment-back/src/api/deps.py` 仍存在 `DEBUG` 下无凭据返回 debug 用户的逻辑
- `investment-back/main.py` 仍可能在启动时自动创建测试用户
- `investment-back/src/core/config.py` 仍存在默认 `SECRET_KEY`、默认 `DEBUG=True`、默认 `AI_API_KEY`
- 前端请求层仍优先按旧 `detail` 风格解析错误

这意味着“目标共享基线”和“当前实现”在访问边界上已经分叉。此 change 的作用不是扩大产品范围，而是把真实环境的认证与配置门槛写得更硬，再将这些稳定约束映射到当前实现中的路由保护、启动校验、日志策略和前端错误消费中，作为后续实现收口和灰度发布的前提。

## Goals / Non-Goals

**Goals:**

- 将受保护业务访问的默认策略固定为 fail-closed，而不是优先满足开发便利
- 明确生产与真实内测环境禁止隐式 debug 身份和运行时测试用户注入
- 明确关键安全配置与日志脱敏的生产门槛
- 让前后端与 QA 对 401/403、会话失效和日志脱敏使用同一套 contract

**Non-Goals:**

- 不在本 change 中决定手机号登录还是邮箱登录的最终实现路线
- 不在本 change 中完成完整的刷新令牌表结构或会话撤销实现细节
- 不覆盖观察列表、复盘闭环或分析结果结构的其他 contract 收口工作

## Decisions

### 决策 1：所有受保护业务接口统一采用 fail-closed 认证策略

选择：

- 缺失 token、token 无效、会话过期和越权访问，全部走统一的 401/403 错误路径
- 请求链路中不允许再创建 debug 用户，也不允许隐式放行

理由与取舍：

- 这样可以直接满足 `auth-session` baseline，也能让前端和 QA 建立稳定的错误状态映射
- 这里保留 401/403、token 与路由保护等表述，是因为本 design 文档负责描述当前实现如何承载共享基线，而不是重新定义 baseline 文案
- 被放弃的方案是“保留 debug fallback，但仅在 `DEBUG=True` 时启用”，因为真实环境一旦发生配置漂移，最容易造成隐式泄漏

### 决策 2：测试身份能力只能通过显式 dev/test 配置或 dev seed 提供

选择：

- 从运行时请求链路和应用启动过程中移除自动测试用户注入
- 将测试身份能力收口到显式 dev/test 认证配置与独立 dev seed

理由与取舍：

- 这样可以将开发便利能力和真实环境能力彻底隔离，避免生产数据与测试身份混写
- 被放弃的方案是“保留启动时自动 seed，只在空库时执行”，因为这仍会将运行时环境和数据治理边界耦合在一起

### 决策 3：生产关键配置必须在启动阶段校验，不允许默认可用值继续兜底

选择：

- 生产环境必须显式提供关键密钥和环境配置
- 生产环境默认关闭 `DEBUG`，并禁止默认 AI key 继续作为可用兜底值

理由与取舍：

- 这样可以把问题提前暴露到启动阶段，而不是等到运行时才留下安全漏洞
- 这些 `SECRET_KEY`、`DEBUG`、`AI_API_KEY` 等名称属于当前实现中的具体配置项，应在 design 和任务层落地，而不再提升为 baseline requirement 的主叙述
- 被放弃的方案是“允许默认值存在，但通过文档提醒不要使用”，因为文档提醒无法替代强制门槛

### 决策 4：前端错误消费以统一 `error` 对象为主，旧 `detail` 只作为短期兼容

选择：

- 401/403 和常见后端异常统一按 `error.code / error.message / error.request_id / error.retryable` 消费
- 若后端仍存在旧接口，可以临时兼容 `detail`，但不能再以 `detail` 为主 contract

理由与取舍：

- 这样能把错误体验和日志追踪口径统一起来，减少联调时的歧义
- 这里显式保留 `error.code / error.message / error.request_id / error.retryable`，因为它属于共享 contract 本身，而不是仅限于单个实现文件的细节
- 被放弃的方案是继续让前端“猜测”错误格式，因为这会把认证异常和普通失败混成一类体验

## Risks / Trade-offs

- [开发调试摩擦上升]：需要补显式 dev seed、测试认证入口和更清晰的本地开发说明
- [历史代码兼容成本增加]：需要分阶段处理旧 `detail` 错误格式和旧登录态逻辑
- [生产启动失败更早暴露]：需要在部署脚本和环境配置文档中同步补齐必填项说明
- [前后端联调节奏受影响]：需要先冻结错误 contract，再并行推进前后端改造和 QA 验证

## Migration Plan

1. 先冻结本 change 的 proposal、delta specs、design、tasks，并将验收口径映射到执行板
2. 后端移除 debug fallback、运行时测试用户注入和默认安全配置兜底
3. 后端统一 401/403 与错误响应结构，前端同步切换错误解析和登录态反馈
4. QA 按认证与降级专项测试集执行验证，确认无 token、token 失效、越权和生产日志脱敏都满足基线
5. 验证通过后，再考虑将该 change 归档并回写 baseline specs

## Open Questions

- 当前项目在真实内测阶段优先使用邮箱验证码登录还是手机号验证码登录，是否需要影响刷新令牌的存储策略
- 生产启动校验失败时，是否需要区分“阻止启动”的硬错误和“允许启动但强告警”的软错误
- 前端兼容旧 `detail` 错误格式的过渡窗口预计保留多久
