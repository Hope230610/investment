# AI 投资决策助手 上线检查清单

更新时间：2026-03-26

## 1. 文档目的

本清单用于在产品从内测走向灰度和正式上线前，统一检查产品、技术、数据、运营、合规和应急能力是否达到最低可上线标准。

本清单不用于判断“产品是否完美”，而用于判断“产品是否具备可控上线能力”。

## 2. 上线原则

- 先小范围灰度，再逐步放量
- 先保证产品边界清晰，再扩大用户规模
- 先保证异常可观测，再追求功能完整
- 先保证数据可降级，再追求分析丰富度
- 先保证用户理解不跑偏，再考虑增长放大

## 3. 上线阶段定义

### 3.1 阶段 A：封闭内测
目标：
- 核心流程可用
- 主要文案和交互逻辑稳定
- 用户不会明显误解产品定位
- 异常问题可被快速发现

用户规模建议：
- 10 到 50 人

### 3.2 阶段 B：灰度上线
目标：
- 主流程稳定
- 数据链路基本可控
- 产品边界和风险提示已成型
- 有最小监控和应急能力

用户规模建议：
- 100 到 500 人

### 3.3 阶段 C：正式上线
目标：
- 主业务流程闭环
- 工程、监控、发布、回滚、客服、合规均具备最小生产能力
- 可支撑持续运营

用户规模建议：
- 逐步放量，不建议一次性大规模开放

## 4. Go / No-Go 判断标准

### 4.1 可以进入灰度的条件
- 登录、画像、单股咨询、交易前自检、交易后复盘、记录、复盘任务全部跑通
- 产品不再保留明显开发态逻辑
- 关键用户数据已实现服务端持久化或已明确收口
- 外部数据异常时有清晰降级策略
- 结果页文案不构成直接交易建议
- 关键错误可通过日志定位
- 基本 smoke checklist 已完成

### 4.2 不可上线的情形
- 仍存在默认测试账号放行逻辑
- 用户关键数据会因换设备丢失
- 外部数据失败时结果页仍输出误导性结论
- 文案中存在明显荐股、收益承诺、交易指令表达
- 关键流程没有异常处理
- 发布后无回滚方案
- 用户反馈显示大量误解产品为荐股工具

## 5. 产品检查清单

- [ ] 产品定位统一为“决策辅助 / 行为干预 / 复盘工具”
- [ ] 所有页面无“荐股、投顾、稳赚、抄底、买点、卖点”等高风险表达
- [ ] 首页、结果页、登录后首屏均有清晰风险声明
- [ ] 三大核心场景的入口逻辑清晰
- [ ] 结果页核心结构稳定
- [ ] “下一步”动作全部为观察、等待、自检、复盘类动作
- [ ] 高风险输入优先触发行为干预
- [ ] 数据不足时明确提示“暂不形成明确判断”
- [ ] 观察列表若未闭环，已明确弱化或隐藏
- [ ] 所有关键文案已统一，不存在乱码和歧义

## 6. 技术检查清单

- [ ] 开发、测试、生产环境口径明确
- [ ] 生产环境关闭 debug 回退逻辑
- [ ] 不再自动创建测试用户
- [ ] 登录认证、token、未登录访问拦截流程稳定
- [ ] API 错误返回格式统一
- [ ] 前端异常态、加载态、失败态可用
- [ ] 外部行情与公告接口有超时、失败、降级机制
- [ ] 日志能定位分析任务失败原因
- [ ] 健康检查接口可用
- [ ] Docker 或正式部署链路与实际依赖一致
- [ ] 发布脚本与 README、部署文档一致

## 7. 数据检查清单

- [ ] 分析记录可稳定保存和查询
- [ ] 复盘任务可稳定生成和查看

- [ ] 核心分析结果保留时间戳
- [ ] 核心理由区分事实、推理、不确定
- [ ] 数据源失败时不会伪造完整结论
- [ ] 分析结果有有效期与复盘时间
- [ ] 数据备份方案明确
- [ ] 敏感数据访问权限明确

- [ ] 投诉升级路径已明确
- [ ] 重大误解或负面舆情预案已准备

## 12. 灰度发布策略

### 12.1 灰度原则
- 从小用户池开始
- 按用户批次逐步放量
- 每一批放量前先看指标
- 出现高风险问题立即暂停放量

### 12.2 灰度节奏建议
第一批：
- 20 到 50 人
- 重点观察主流程稳定性和误解率

第二批：
- 50 到 150 人
- 重点观察行为指标和复盘率

第三批：
- 150 到 500 人
- 重点观察留存、错误率、投诉率

### 12.3 灰度放量决策指标
- 分析完成率稳定
- 高风险场景误导率低
- 用户误解率下降
- 外部数据失败率可控
- 无重大合规投诉
- 无严重稳定性事故

## 13. 回滚方案

### 13.1 必须具备的回滚能力
- 可快速回退前端版本
- 可快速回退后端版本
- 可关闭新入口或高风险功能
- 可暂停灰度放量
- 可关闭外部数据依赖的高风险功能
- 可临时降级为只展示基础信息和风险提示

### 13.2 触发回滚的情形
- 关键接口持续异常
- 结果页错误率异常上升
- 用户大规模误解产品为荐股工具
- 数据源异常导致结论失真
- 认证系统异常
- 高风险投诉或舆情出现
- 合规风险被识别

### 13.3 回滚后的优先动作
- 暂停放量
- 定位问题
- 明确影响范围
- 对内同步结论
- 对外统一口径
- 修复完成后重新小流量验证

## 14. 应急响应方案

### 14.1 P0 事故
定义：
- 无法登录
- 无法生成分析
- 结果页大面积失败
- 数据输出明显错误或高风险越界
- 用户投诉存在明显“荐股诱导”

要求：
- 立即响应
- 立即暂停放量
- 立即进入事故处理流程

### 14.2 P1 事故
定义：
- 部分接口失败
- 外部数据源不稳定
- 复盘任务异常
- 局部场景文案误导

要求：
- 当天处理
- 明确修复时间
- 必要时局部降级

### 14.3 P2 问题
定义：
- 非关键页面体验问题
- 文案表达不清晰
- 次要流程转化偏低

要求：
- 纳入下一轮版本优化

## 16. 上线后 24 小时重点观察项

- 登录成功率
- 分析成功率
- 结果页错误率
- 外部数据源失败率
- 高情绪场景触发情况
- 用户误解反馈
- 用户投诉数量
- 白屏率
- 401 比例
- 复盘任务是否正常生成

## 17. 上线后 7 天复盘项

- 三大场景实际使用结构
- 哪个场景最有价值
- 哪个场景最弱
- 用户是否形成复盘回流
- 用户是否将产品误解为荐股工具
- 哪类用户留存最好
- 哪类用户流失最快
- 数据异常是否对产品信任造成影响
- 是否具备继续放量条件

## 18. 最终上线建议

只有当以下条件同时满足，才建议进入更大范围上线：
- 主链路稳定
- 用户理解稳定
- 数据链路可控
- 风险边界明确
- 异常可观测
- 回滚可执行
- 合规风险已被充分评估
