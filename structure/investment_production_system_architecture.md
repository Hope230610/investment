# AI 投资决策助手 生产系统架构方案

更新时间：2026-03-30

## 1. 文档目的

本方案用于把当前产品方案进一步收口为可开发、可联调、可内测、可灰度的生产级系统架构。

本方案重点回答以下问题：

- 产品要落地为哪些核心系统模块
- 各模块之间如何通信
- 哪些链路必须异步化
- 外部数据、分析任务、结果页、复盘任务如何形成闭环
- 如何在 MVP 阶段兼顾可维护性、可扩展性、成本和可靠性

## 2. 架构目标

### 2.1 产品目标反推的架构目标

从“决策辅助 + 行为干预 + 复盘闭环”的产品目标反推，系统必须满足：

- 三大核心场景稳定可用
- 分析任务可异步处理，避免同步阻塞
- 数据源异常时可降级，不输出误导结论
- 结果页、历史记录、复盘任务形成服务端闭环
- 所有关键行为和失败链路可观测
- 支持封闭内测到灰度上线的渐进放量

### 2.2 架构原则

- 优先选择最合适方案，不追求复杂架构炫技
- 读写链路分离，分析链路异步化
- 以服务端持久化为主，前端缓存只做体验优化
- 先保证可降级、可回滚、可观测，再追求分析丰富度
- 单模块可以先以单体部署实现，但模块边界必须清晰

## 3. 总体架构结论

当前阶段建议采用：

- `前端 Web 应用`
- `后端 API / BFF 服务`
- `分析编排与任务队列`
- `分析 Worker 服务`
- `市场数据聚合服务`
- `PostgreSQL 主库`
- `Redis`
- `对象存储/日志平台/监控平台`

部署形态建议为：

- 逻辑上模块化
- 物理上允许前期采用“单仓 + 少量服务”部署
- 所有重分析、外部依赖、回流任务均走异步链路

## 4. 系统模块拆分

### 4.1 前端应用

职责：

- 承载登录、画像、三大分析场景、结果页、历史记录、复盘任务页
- 负责表单校验、状态展示、失败提示、过期提示
- 负责发起分析任务和轮询/订阅任务状态
- 负责最小行为埋点

不负责：

- 拼装投资结论
- 直接判断数据是否足够
- 绕过服务端做关键状态持久化

### 4.2 API / BFF 服务

职责：

- 对前端提供统一 API 契约
- 负责认证、鉴权、用户画像、记录、复盘任务、观察列表读写
- 创建分析任务并写入数据库
- 编排异步任务投递
- 聚合分析状态，向前端返回统一 ViewModel

选择理由：

- 减少前端直接拼装多个后端服务的复杂度
- 更适合统一产品边界、错误格式和降级口径

### 4.3 分析编排服务

职责：

- 接收分析任务
- 决定分析流程和优先级
- 调用市场数据聚合服务获取输入
- 调用规则层和模型层
- 生成结构化结果
- 决定是否创建行为干预与复盘任务

设计要求：

- 必须异步执行
- 不对前端直接暴露
- 出错时可重试、可超时、可标记降级

### 4.4 分析 Worker

职责：

- 消费分析任务队列
- 拉取所需基础数据
- 执行规则判断、画像适配、提示词构造、模型推理
- 将结构化结果写回数据库

说明：

- Worker 可以和编排服务先部署在同一服务中
- 但代码边界要分离，便于后续扩展为独立 Worker

### 4.5 市场数据聚合服务

职责：

- 统一接入行情、公告、基础信息等外部数据
- 对外部数据源做超时、熔断、缓存、失败降级
- 向分析服务提供统一标准化输出

必要性：

- 外部数据源是系统最不稳定部分，必须单独隔离
- 统一聚合有利于替换供应商、控制字段质量和降级策略

### 4.6 PostgreSQL

职责：

- 存储用户、画像、股票、分析任务、分析结果、干预记录、复盘任务、用户操作记录
- 提供主业务查询和追踪能力

要求：

- 主业务强一致数据全部落 PostgreSQL
- 每日备份
- 支持恢复演练

### 4.7 Redis

职责：

- 任务队列
- 短期缓存
- 幂等键
- 高频查询缓存
- 限流和简单会话辅助

说明：

- Redis 不作为核心事实存储
- 用户关键记录不得仅存在 Redis

### 4.8 监控与日志系统

职责：

- 收集 API 请求、任务耗时、外部数据失败率、错误率、白屏率、401 比例
- 支持按 `analysis_id`、`user_id`、`stock_id` 追踪问题
- 支持告警

## 5. 核心数据流

### 5.1 分析任务主链路

```text
前端提交分析
→ API 校验请求和用户身份
→ 写入 analysis_tasks(status=processing)
→ 投递消息到任务队列
→ Worker 消费任务
→ 拉取用户画像快照和市场数据
→ 执行规则判断 / 模型推理 / 降级判断
→ 写入 analysis_results
→ 更新 analysis_tasks(status=ready/partial_ready/failed)
→ 生成 review_tasks / behavior_interventions
→ 前端轮询或刷新结果页获取最终状态
```

### 5.2 外部数据调用链路

```text
分析 Worker
→ 市场数据聚合服务
→ 行情源 / 公告源 / 基础信息源
→ 标准化清洗
→ 命中缓存则直接返回
→ 失败则返回标准化降级状态
```

### 5.3 复盘任务闭环

```text
分析结果 ready
→ 创建 review_task
→ 首页 / 复盘页展示待复盘
→ 用户完成复盘
→ 写入 review_tasks / user_actions
→ 进入历史记录和指标看板
```

## 6. 异步设计要求

根据 Architect 规则，模块间通信优先异步。

必须异步的链路：

- 分析任务执行
- 复盘任务生成
- 用户行为埋点入库
- 外部数据预拉取或缓存刷新
- 告警通知

可以同步的链路：

- 登录
- 获取画像
- 查询历史记录
- 查询待复盘任务

取舍说明：

- 用户请求链路只保留“必须立即反馈”的同步操作
- 计算重、依赖多、失败概率高的部分全部异步化

## 7. 部署建议

### 7.1 MVP 到内测阶段

建议最小部署单元：

- `web`：前端静态站点
- `api`：BFF + 轻量编排
- `worker`：异步分析任务执行
- `postgres`
- `redis`

### 7.2 灰度阶段

建议补强：

- API 与 Worker 独立扩缩容
- 外部数据聚合服务从 API 中拆出
- 日志与监控独立平台化
- 引入负载均衡和最小 WAF/网关

## 8. 可扩展性设计

### 8.1 横向扩展点

- Worker 可按任务量横向扩容
- API 可按请求量横向扩容
- Redis 队列可扩为专业消息队列
- 数据源聚合服务可扩展多供应商

### 8.2 纵向扩展点

- 增加更多场景时只扩展 `scenario` 编排规则
- 增加更复杂解释层时只扩展 `explanation_layer`
- 增加更多数据源时只扩展聚合服务适配器

## 9. 成本与复杂度取舍

当前不建议：

- 一开始拆成过多微服务
- 一开始引入复杂流式架构
- 一开始做多区域部署

当前建议：

- 模块边界明确，但部署保持节制
- 用 Redis 队列承接 MVP 异步需求
- 先把观测、降级和一致性做好

## 10. 可靠性要求

### 10.1 高可用最小要求

- API 至少双实例
- Worker 至少双实例
- PostgreSQL 有自动备份
- Redis 启用持久化
- 关键功能具备开关

### 10.2 容错要求

- 外部数据源失败不得直接把错误透传为强结论
- 模型调用失败可重试一次，仍失败则降级
- 分析超时进入 `failed` 或 `partial_ready`
- 结果页必须可展示失败态和重试建议

## 11. 监控与日志

必须监控：

- 登录成功率
- 分析任务创建成功率
- 分析任务完成率
- 分析平均耗时
- 外部数据失败率
- 结果页加载失败率
- 401 比例
- 复盘任务生成成功率

日志追踪最小字段：

- `request_id`
- `analysis_id`
- `user_id`
- `stock_id`
- `scenario`
- `status`
- `error_code`
- `degrade_reason`

## 12. 备份与恢复要求

### 12.1 备份

- PostgreSQL 每日全量备份
- 关键表支持更高频逻辑备份
- 配置和迁移文件纳入版本管理

### 12.2 恢复

- 明确恢复步骤
- 每月至少做一次恢复演练
- 恢复后要验证分析记录、复盘任务、画像数据完整性

## 13. 架构结论

当前最合适的方案不是“最复杂的 AI 系统”，而是：

- 以前后端分离为基础
- 以 API/BFF 收口产品接口
- 以异步任务承接分析执行
- 以数据聚合服务隔离外部不稳定性
- 以 PostgreSQL + Redis + 监控日志支撑可用性

这套架构足以支撑封闭内测到灰度上线，并为后续扩展留出清晰边界。
