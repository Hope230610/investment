# AI 投资决策助手 认证与权限设计方案

更新时间：2026-03-30

## 1. 文档目的

本方案用于解决当前项目从 MVP 向可上线产品推进时最关键的身份与权限问题。

目标是：

- 关闭开发态认证逻辑
- 建立稳定的登录、鉴权、会话管理方案
- 明确普通用户、运营、管理员的权限边界
- 确保用户关键数据不会因认证设计粗糙而越权访问

## 2. 当前问题

结合现有文档，当前项目已明确存在以下阻塞项：

- 仍可能保留 debug 用户回退逻辑
- 启动时自动创建测试用户
- token 失效和未登录拦截逻辑未完全收口
- 上线文档和迁移示例中仍混有测试账号思路

这说明认证能力仍停留在 MVP 阶段，不适合直接进入真实内测。

## 3. 设计目标

- 所有真实用户访问都必须基于正式身份
- 无 token 或 token 无效时，不得自动放行
- 用户只能访问自己的画像、分析记录、复盘任务、观察列表
- 后台权限与普通用户权限彻底隔离
- 支持未来扩展灰度开关、运营审核、投诉处理

## 4. 角色定义

### 4.1 普通用户 `user`

可访问：

- 自己的用户画像
- 自己的分析任务与结果
- 自己的复盘任务
- 自己的观察列表
- 自己的行为记录

不可访问：

- 其他用户任何数据
- 系统配置写操作
- 运营看板明细
- 敏感日志

### 4.2 运营角色 `operator`

可访问：

- 内测用户池管理
- 用户反馈列表
- FAQ 与运营文案配置
- 脱敏后的指标与投诉记录

不可访问：

- 用户原始密码信息
- 全量敏感行为详情
- 直接修改分析结果事实数据

### 4.3 管理员 `admin`

可访问：

- 系统配置
- 灰度开关
- 事故处置开关
- 监控看板
- 运维级别审计信息

限制：

- 所有管理员操作必须可审计
- 高风险操作应通过白名单或二次确认控制

## 5. 登录方案建议

### 5.1 当前阶段建议

建议采用：

- 手机号验证码登录，或
- 邮箱验证码登录

不建议在当前阶段优先投入：

- 复杂第三方社交登录
- 多因子企业级登录

理由：

- MVP 和内测阶段重点是降低登录摩擦
- 验证码登录更符合普通用户场景

### 5.2 会话模型

建议采用：

- 短期访问令牌 `access token`
- 长期刷新令牌 `refresh token`

要求：

- `access token` 过期时间短
- `refresh token` 可撤销
- 服务端保留刷新令牌状态

## 6. 鉴权规则

### 6.1 API 鉴权要求

所有以下接口必须鉴权：

- `/api/v1/user/*`
- `/api/v1/analysis/*`
- `/api/v1/reviews/*`
- `/api/v1/records/*`
- `/api/v1/watchlists/*`

可匿名访问范围应极小：

- 健康检查
- 静态风险说明页

### 6.2 资源级鉴权

除角色鉴权外，必须增加资源归属鉴权。

例如：

- 用户读取 `analysis/:id` 时，必须校验该记录属于当前用户
- 用户读取 `review_task` 时，必须校验 `user_id`
- 用户更新画像时，只能更新自己的画像

## 7. Token 设计

### 7.1 Access Token

建议承载字段：

- `sub`
- `role`
- `session_id`
- `issued_at`
- `expires_at`

### 7.2 Refresh Token

要求：

- 服务端保存哈希值而不是明文
- 支持单设备撤销
- 支持全局登出

## 8. 会话失效处理

### 8.1 后端处理

- token 失效统一返回 401
- 返回统一错误码和错误文案
- 不允许 fallback 到默认用户

### 8.2 前端处理

- 收到 401 后尝试刷新会话
- 刷新失败则清除本地会话并跳回登录
- 保留“登录后返回原页面”体验

## 9. 开发态逻辑下线要求

上线前必须关闭：

- 无 token 返回测试用户
- 启动时自动创建测试账号
- 通过 query 或本地标记强制伪装登录
- 前端写死用户身份

替代方案：

- 测试环境使用单独测试数据和测试认证配置
- 通过环境变量隔离 dev/test/prod

## 10. 权限矩阵

| 资源 | user | operator | admin |
| --- | --- | --- | --- |
| 读取自己的画像 | 是 | 否 | 是 |
| 修改自己的画像 | 是 | 否 | 是 |
| 读取自己的分析记录 | 是 | 否 | 是 |
| 读取其他用户明细 | 否 | 脱敏受限 | 是 |
| 修改系统配置 | 否 | 否 | 是 |
| 管理灰度开关 | 否 | 否 | 是 |
| 查看反馈与投诉 | 否 | 是 | 是 |

## 11. 审计要求

以下操作必须审计：

- 管理员修改系统配置
- 开关高风险功能
- 导出敏感数据
- 修改灰度策略
- 撤销用户访问资格

审计字段至少包括：

- 操作人
- 操作时间
- 操作对象
- 操作前后摘要
- 请求来源 IP

## 12. 安全要求

- 密码场景下只存哈希，不存明文
- 刷新令牌服务端可撤销
- 敏感接口限流
- 登录接口防刷
- 后台接口必须走更严格白名单或内网保护

## 13. 落地优先级

### P0

- 关闭 debug 放行逻辑
- 关闭自动创建测试用户
- 完成统一鉴权中间件
- 完成资源级权限校验
- 完成 401 与会话失效统一处理

### P1

- 管理员审计日志
- 单设备会话管理
- 更细权限分层

## 14. 结论

当前最重要的不是做复杂权限体系，而是先把“真实用户身份”和“数据归属边界”做扎实。

只要做到：

- 没有默认放行
- 没有测试身份混入生产
- 用户只能访问自己的数据
- 管理权限有明确边界

项目才具备进入真实内测的认证基础。
